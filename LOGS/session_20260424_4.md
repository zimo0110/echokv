### 2. RULER-32K CUDA OOM

**Symptom:** `torch.OutOfMemoryError: Tried to allocate 95.38 GiB` on
every RULER-32K request. The OOM occurs in
`transformers/masking_utils.py::causal_mask_function` which materialises
the full `(B, H, Lq, Lk)` float32 causal mask — for Lq=Lk=32K:
`1 × 32 × 32000 × 32000 × 4 bytes ≈ 131 GB`, exceeding the H100's
79 GB.

**Root cause in `_ruler_sample`:** the original formula was
`filler_rep = max(1, target_tokens // 3)` with a comment `# ~3 words
per cycle`. `_RULER_FILLER` actually has ~22 words / ~31 BPE tokens per
cycle. With `target_tokens=32_000`, `filler_rep=10666`, producing
~300K-word prompts. The tokenizer (called with `truncation=False`)
passed the full prompt to the model, causing the causal mask to materialise
at ~27-32K actual tokens — enough to OOM.

**Fix** (`evaluation/motivation/workloads.py`):
- Changed formula: `filler_rep = max(1, target_tokens * 4 // len(_RULER_FILLER))`
  (4 chars/BPE token estimate; `_RULER_FILLER` = 125 chars ≈ 31 tokens/rep).
- Changed `target_tokens` default from `32_000` to `4_000`.
- Verified: resulting prompt is 16,135 chars / ~3014 words / ~4018 tokens.
- At 4K context: causal mask = `1×32×4K×4K×4 = 2.1 GB` → fits in 60 GB free.

**Note:** RULER-4K is weaker than RULER-32K as a test — 100% accuracy
at 4K context means zero accuracy variance (see gate results below).
The intended 32K experiment requires FlashAttention (or equivalent
chunked attention) to avoid materialising the full L×L mask.

### 3. Diagnosis of gate failure

The FAIL is driven by two experimental artifacts:

**Artifact A — max_new_tokens=64 for GSM8K-CoT:**
CoT reasoning requires 150–400 tokens to write out a step-by-step
solution and produce the final answer. With 64 max tokens, the model
is truncated mid-reasoning and the `_extract_gsm8k_answer` regex rarely
matches. Result: 3.75% accuracy (15/400 correct) vs expected 60–70%.
The near-zero accuracy leaves no useful variance (σ=0.19 is from the
binary 0/1 distribution at near-zero mean — mostly 0s with a few 1s).
With near-zero mean, the 1s are essentially random successes; ρ≈0.

**Artifact B — RULER-4K trivially easy:**
At 4K context the model retrieves the needle 100% of the time (acc=1.0,
σ=0.0). The task needs ≥8K context to produce accuracy variance under
INT4 compression. The 4K reduction was necessary to avoid OOM (see Bug 2
above), but it invalidated RULER as a gate workload.

**δ measurements are healthy:**
δ grows monotonically with prompt length — sharegpt (0.0039) <
humaneval (0.0117) < gsm8k (0.0147) < summarization (0.0229) <
ruler_4k (0.0367). Longer context → more KV cache quantized → larger
KL divergence. This is physically correct and consistent with KIVI
paper results.

### Diagnosis

**RULER ceiling persists at 8K.** The model retrieves the needle 100% of
the time even with INT4 KV compression at 8K context. Llama-3.1-8B-Instruct
is too capable for 8K NIAH to show accuracy degradation. To get variance
we need ≥16K context. But delta at 16K = 2 × 32 × 16K² × 4 B = 66 GB/layer
— impossible on a single H100 without chunked delta computation.

**GSM8K still truncated at 256 tokens.** All 400 completions hit exactly
`max_new_tokens=256`. Llama-3.1-8B-Instruct CoT chains need 300-600 tokens
for typical GSM8K problems. At 256 tokens the model is always cut off before
reaching the final answer; `_extract_gsm8k_answer` then hits the fallback
(last number in partial output), which is almost never the correct answer.
Only 4/400 were accidentally correct. The σ = 0.099 falls just below the
0.10 gate threshold (which would have triggered `undetermined` anyway, not
`informative`). Fix: `max_new_tokens ≥ 512`.

**Note on v1 vs v3 GSM8K accuracy:** v1 showed 3.75% accuracy (15/400
correct) with max_new_tokens=64 — this was worse truncation but a higher
"random hit" rate because shorter completions happened to end on matching
numbers from intermediate calculations.
