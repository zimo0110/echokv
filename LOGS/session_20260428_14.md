# Session 14 — Multi-needle RULER (Step 1 of critic's prioritized plan)

**Date:** 2026-04-28
**Goal:** test whether forcing the model to retrieve 5 distinct
needles from one long context breaks INT4 on Llama-3.1-8B. If
INT4 drops below FP16 by ≥0.05 at any tested context, that's
the workload EchoKV-3C has been waiting for.

## Hypothesis

Single-needle RULER (Sessions 8–13) lets attention concentrate
on one position; per-key INT4 noise gets amortized. If we insert
5 labeled needles spread across the haystack and ask the model
to retrieve all 5 in a single answer, attention has to remain
sharp on multiple positions during decode. Per-key noise should
accumulate enough to push at least one needle off the right
value.

## What was implemented

### `_ruler_multineedle_sample` in `evaluation/motivation/workloads.py`

Generates a haystack with `n_needles=5` labeled magic numbers
(`alpha`/`bravo`/`charlie`/`delta`/`echo`, each a 6-digit
random integer). Insertion points are evenly spread across the
body (10–90% region) with random jitter inside each segment.
Label-to-position pairing is shuffled so the model can't infer
order from filler context. The reference uses a fixed canonical
label sequence, so scoring is independent of insertion order.

Score = fraction of `n_needles` correctly recovered (0/5 …
5/5). Per-label match: regex finds `<label>=<digits>` in the
completion.

### `evaluation/serving/run_session14_multineedle.py`

New driver, mostly composes existing pieces:
- `make_multineedle_prompts()` — wraps the new generator.
- `run_cell()` — same 1-phase / 2-phase logic as
  `run_session11_sweep.run_cell`, only with the new prompt
  builder.
- Defaults: 30 prompts × 5 needles per cell,
  `max_new_tokens=128` (must fit five `label=NNNNNN` lines).
- Configs: `fp16` and `static_int4` only by default; pass
  `--configs fp16 static_int4 echokv_3c` once a break is
  observed.

### Fractional-scoring fix in `evaluation/serving/run_session8.py`

The first sweep returned a strange bimodal distribution
(only `0.0` and `1.0` per-prompt scores, no partial credit).
Inspection revealed `_extract_metrics` was casting the score
to `int`:

```python
correct = int(req.score_fn(completion_text)) if req.score_fn else 0
```

That collapses 0.8/0.6/0.4/0.2 to 0. Fix:

- `RequestMetrics.correct: int` → `float`.
- Drop the `int(...)` cast; preserve the workload's float score.
- Add `completion_text: Optional[str] = None` to the per-request
  blob so failure-mode analysis doesn't require re-running.

Binary workloads (single-needle RULER, GSM8K) are unaffected —
`int(0.0) == 0` and `int(1.0) == 1` are the only values they
ever see.

| 128K | 0.833 | 0.860 | +0.027 ± 0.041 | 728s / 768s |

Per-prompt distribution at 128K (30 prompts × 5 needles):

| cfg | #1.0 | #0.8 | #0.6 | #0.4 | #0.2 | #0.0 |
|---|---:|---:|---:|---:|---:|---:|
| FP16 | 20 | 2 | 4 | 1 | 3 | 0 |
| INT4 | 21 | 0 | 7 | 1 | 1 | 0 |

Paired comparison at 128K: 25/30 prompts identical between
FP16 and INT4, 3 INT4-worse, 2 INT4-better. The two
distributions are essentially the same.

## Failure-mode inspection (128K FP16 partial-credit completions)

```
score=0.80: ' alpha=326614\nbravo=549489\ncharlie=870517\ndelta=774723\necho=326614\n...'
score=0.60: ' alpha=747229\nbravo=550395\ncharlie=949066\ndelta=404148\necho=561731\n...'
score=0.20: ' alpha=888652\nbravo=904565\ncharlie=990192\ndelta=234755\necho=785667\n...'
```

Note the score=0.80 case: model writes `alpha=326614` and
`echo=326614` — same value pasted under two different labels.
That's an attention-confusion failure (model retrieved one
needle but lost track of which label it should pair with), not
a KV-quantization failure. The KV cache preserved `326614`
exactly; the model just bound it to the wrong key.

This pattern repeats across the 0.6 and 0.2 cases: distinct
6-digit numbers per label, but several are wrong. The model is
attending to *some* position(s) but not the right ones.

## Verdict

INT4 does **not** degrade vs FP16 on multi-needle 5-key RULER
at any context up to 128K. Combined with Session 13's single-
needle results, we've now tested 6 (workload, context)
combinations on Llama-3.1-8B and KIVI-style group-32 INT4
matches FP16 on every one within noise. The closed-loop
controller continues to have nothing to improve on accuracy.

## Next steps (per the critic's prioritized plan)

1. **LongBench multi-hop QA (Step 2)** — HotpotQA or
   2WikiMultihopQA. Two structural differences from RULER:
   supporting facts are embedded in natural prose (harder for
   attention to localize), and the model must combine retrieved
   facts via reasoning (not just transcribe them). The
   reasoning step is where KV noise plausibly compounds. Run
   under FP16 + static INT4 + static INT2 at the dataset's
   native context lengths. Score with exact-match.

2. **Llama-3.1-70B on RULER@128K (Step 3, only if Step 2
   fails)** — 8× larger KV cache, stronger but more KV-dependent
   representations. Multi-GPU (TP=8 or 4) setup, 2-3 hours of
   model-loading prep. The model the paper's economic argument
   is actually about.

3. **Per-tier τ_budget implementation (Session 15+)** — only
   after Step 1, 2, or 3 yields a workload where the closed
   loop has room to operate. On a workload where INT4 already
   saturates accuracy, per-tier τ produces uniform-INT4 results
   faster and not differently.
