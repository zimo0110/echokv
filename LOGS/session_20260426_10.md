showing 27.0 s vs 24.8 s baseline at 32K. The critic flagged this as

### Task B — survey vLLM 0.16 KV cache to scope "the fork"

Direct source inspection of `vllm/v1/`:

- ``kv_cache_dtype`` only accepts ``"auto"`` (FP16/BF16) or ``"fp8"``
  variants. INT4 is not supported.
- ``vllm/v1/attention/ops/triton_reshape_and_cache_flash.py`` is the
  write path. INT4 would need a new branch alongside ``FP8_KV_CACHE``.
- ``vllm/v1/attention/backends/flashinfer.py`` is the read path.
  INT4 would need a dequant inside the FlashInfer call site.
- ``KVCacheSpec`` (in ``vllm/v1/kv_cache_interface.py``) is per-layer-
  *class* today; making it per-layer-*instance* is a refactor of the
  cache coordinator and `kv_cache_utils.py`.
- The strict three-pool architecture (`INT2/INT4/INT8`) per layer
  needs both of the above plus a tier-aware free-list manager.

Honest scope: even the minimal first slice (add ``"int4"`` to
``kv_cache_dtype`` and route through ``simulate_quantization`` on the
write side) is multi-day work that requires cloning vLLM and an
editable install. The full three-pool per-layer fork is multi-session.

### Task C — memory savings projection

Added `CanaryHarness.memory_projection(baseline_bits=16)`. Computes:

- ``per_layer_bits``: list of bits per layer (from
  ``controller.snapshot()``)
- ``avg_bits``: mean over layers
- ``savings_vs_baseline_pct``: 100 × (1 − avg_bits / 16) — the headline
  cell for a paper memory savings claim
- ``savings_vs_kivi4_pct``: 100 × (1 − avg_bits / 4) — negative when
  EchoKV uses more memory than uniform INT4 (informative for the
  Pareto framing)
- per-bit tier counts

Surfaced in `report()` and printed in `run_session8.py`'s EchoKV-3C
summary block. The number is **derived from a real measurement** —
the controller's tier vector chosen against real RULER inference —
even though vLLM's cache is still FP16 on the GPU. The computation is
the same one a real fork would produce.

## Real numbers (memory)

RULER, Llama-3.1-8B-Instruct, single H100:

| context | n  | tier vector              | avg bits | **savings vs FP16** | savings vs KIVI-4 | accuracy |
|---------|----|--------------------------|----------|----------------------|--------------------|----------|
| 4K      | 50 | 1 INT2 / 0 INT4 / 31 INT8 | 7.81     | **+51.2%**           | -95.3%             | 1.000    |
| 32K     | 20 | 8 INT2 / 0 INT4 / 24 INT8 | 6.50     | **+59.4%**           | -62.5%             | 1.000    |

The 32K row is the more meaningful one — at 32K context on RULER,
EchoKV-3C cuts KV cache memory by **59.4%** vs FP16 baseline while
RULER accuracy stays at 1.000. KIVI-4 (uniform INT4, 75% savings vs
FP16) saves more memory; the controller traded back some of that
budget to upgrade 24 of 32 layers to INT8 in service of preserving
accuracy.

This is the first **paper cell that is not TBD** — and it's not a
guess. The tier vector is a real measurement; the math is identity.

## What this session does NOT solve

The Pareto story the paper needs ("EchoKV beats KIVI-4 on a workload
where KIVI-4 hurts") requires a workload where static KIVI-4 actually
fails. RULER@32K on Llama-3.1-8B-Instruct is not that workload —
all three configs (FP16, KIVI-4-equivalent, EchoKV-3C) produce 1.000
accuracy. To show the Pareto win we need either longer context (64K,
128K) on a weaker model, or a different task (math, code, summary)
that genuinely stresses INT4 KV. Picking that workload — and getting
a real KIVI-4 baseline once the fork lands — is Session 11+.
