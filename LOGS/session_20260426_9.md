# Session 9 — 2026-04-27

## Goal

Two pieces, in the order the critic prioritised:

1. **Fix the canary overhead at 32K.** Session 8's Python forward-pre-
   hook was paying O(L²) per fire because it ran on prefill batches
   with `query.shape[0] = sum_of_prompt_lengths`. The architectural
   canary fires on decode steps only.
2. **Get EchoKV-3C accuracy numbers.** Wire the controller's per-layer
   tier decisions into the actual forward path — the "fork-equivalent"
   without modifying vLLM source. This is the first measurement of
   per-layer dynamic precision affecting inference outputs.

### Task B — decode-only canary + canary CUDA stream

`evaluation/serving/canary_vllm.py::CanaryHarness`:

- New constructor flags: `decode_only_canary: bool = True` (architectural
  default) and `max_decode_tokens: int = 256`.
- In `_maybe_fire`, skip if `query.shape[0] > max_decode_tokens`. This
  catches prefill batches whose query is `sum of prompt lengths` —
  typically thousands at long context.
- New flag `use_canary_stream: bool = True`. The canary's softmax/KL
  is wrapped in `torch.cuda.stream(self._canary_stream)`; the canary
  stream `wait_stream`s the production stream before reading args, and
  the production stream `wait_stream`s the canary stream before the
  pre-hook returns. Synchronous from the model's POV but lets the GPU
  schedule both streams concurrently.
- `_canary_stream` created lazily on first GPU fire (so harness can be
  constructed CPU-only for tests).

### Task C — tier application (vLLM-fork-equivalent)

`evaluation/serving/canary_vllm.py::CanaryHarness._apply_tier_quant`:

- New constructor flags: `tier_application: bool = False` and
  `tier_application_quant_v: bool = True`.
- When active, the pre-hook returns
  `(query, k_quantized, v_quantized) + tuple(args[3:])` where K and V
  are quantised by `simulate_quantization` at
  `controller.level(layer_id)` bits — INT2/INT4/INT8 dispatched per
  layer. The canary fires *first* (read-only on FP16 K) so the
  measurement is on the unquantised signal; then tier application
  mutates args before vLLM's attention sees them.
- `CanaryStats` extended with `tier_applications`, `tier_application_overhead_s`,
  `tier_apply_count_by_bits`.
- Surfaced in `report()` for the post-run JSON.

`evaluation/serving/run_session8.py`:

- New CLI flag `--echokv-3c`. Adds a 4th run config "echokv_3c" that
  installs a fresh harness with `tier_application=True` and seeds the
  controller's per-layer levels from the converged tier vector of the
  observability run (otherwise the EchoKV-3C run starts at uniform
  INT4 and may not differentiate within the run's compute budget).
- Summary block prints the tier vector + per-bit application counts +
  Δacc vs FP16 baseline.

## Real numbers

### Overhead (RULER, single H100)

| run | 4K throughput (tok/s) | 4K overhead | 32K throughput (tok/s) | 32K overhead |
|-----|------------------------|-------------|--------------------------|----------------|
| baseline FP16 | 510.4 | — | 22.6 | — |
| canary @ p_c=1/64 | 502.4 | **+1.57%** | 22.4 | **+0.54%** |

Session 8 reported 32K overhead at +15.07%; session 9 lands at
+0.54% — **28× improvement** from a one-flag fix
(`decode_only_canary=True`). The win is structural: the architectural
canary fires only at decode steps; the session-8 implementation
incidentally fired on prefill batches because the Bernoulli draw
didn't gate on which kind of forward this was. With prefill skipped,
each fire is O(num_decode_tokens × kv_len) ≈ O(L) instead of
O(prefill_len²) ≈ O(L²).

### Accuracy + tier distribution (RULER@32K, EchoKV-3C)

| run | accuracy | wall (s) | throughput (tok/s) | tier vector |
|-----|----------|----------|---------------------|-------------|
| baseline FP16 | 1.000 | 24.8 | 22.5 | n/a |
| canary @ p_c=1/64 (shadow) | 1.000 | 24.9 | 22.4 | n/a |
| **EchoKV-3C** (tier_application=True) | **1.000** | 27.0 | 20.7 | **12 INT2 / 1 INT4 / 19 INT8** |

Final tier vector at the end of the EchoKV-3C run on RULER-32K:

```
L00:INT2  L01:INT8  L02:INT8  L03:INT8  L04:INT8  L05:INT8  L06:INT8  L07:INT8
L08:INT2  L09:INT2  L10:INT2  L11:INT2  L12:INT8  L13:INT2  L14:INT8  L15:INT8
L16:INT8  L17:INT8  L18:INT2  L19:INT8  L20:INT8  L21:INT8  L22:INT8  L23:INT8
L24:INT8  L25:INT8  L26:INT8  L27:INT8  L28:INT2  L29:INT8  L30:INT8  L31:INT8
```

12 layers at INT2, 19 at INT8, 1 at INT4. RULER@32K accuracy stays at
**1.000** — needle-retrieval works correctly under this mix-of-
precisions per-layer KV cache. **Δacc = +0.000 vs FP16 baseline.**

### Accuracy (RULER@4K, EchoKV-3C)

| run | accuracy | tier vector |
|-----|----------|-------------|
| baseline FP16 | 1.000 | n/a |
| **EchoKV-3C** | **1.000** | 1 INT2 / 0 INT4 / 31 INT8 |

At 4K, observed canary δ̂_ℓ is high enough on most layers that the
controller upgrades them to INT8 (more precision). Only layer 0 stays
at INT2. Accuracy still matches FP16.

## Decisions / things worth recording

1. **Decode-only canary is the right default**, not a tuning knob.
   The architectural canary in §4.1 says "with probability 1/64 the
   step is marked canary" — implicitly a decode step. The session-8
   monkey-patch fired indiscriminately and paid O(L²) on prefill
   batches. Fixed in code; flag exists (`--canary-on-prefill`) only
   to allow re-running the bad behaviour for comparison.
2. **Two-stream canary, synchronous result collection.** The pre-hook
   `wait_stream`s before reading the KL via `.item()`. True async
   result collection (CUDA events + deferred fetch at controller-tick
   time) is a future improvement. The current sync still gives the
   GPU room to schedule canary work on a separate stream.
3. **Tier application happens at projection output time** (write-time
   to the cache), not at read-time. This matches KIVI's mechanism:
   quant noise is baked in once when K is written; the cache stores
   the noisy values; future reads see the same baked-in noise. INV-2
   is preserved — a tier change for a layer doesn't re-quantise blocks
   already in cache, only new ones.
4. **Tier-application overhead is simulation cost, not real cost.**
   `simulate_quantization` does per-tensor Python work every forward
   call (32 layers × ~77 forwards = 2464 applications at 32K). A real
   KIVI cache stores INT4 once and pays zero runtime quant cost. The
   accuracy number transfers to a real fork; the wall-clock comparison
   does not. Documented in CHANGELOG.
5. **EchoKV-3C 4th-run controller is seeded from the observability
   run's converged tier vector.** Without seeding the EchoKV-3C run
   starts at uniform INT4 and the controller barely has time to
   differentiate within the run. With seeding the tier vector reflects
   what the controller actually picks given the workload's δ profile.

## What session 10 should start with

Two pieces, prioritised by risk:

1. **Production canary kernel in Triton at the FlashInfer level.**
   The decode-only Python pre-hook is at +0.54% overhead; that's good
   enough to ship as a measurement tool. But the production canary
   wants to live inside FlashInfer's paged decode attention as a
   parallel-stream KL-on-one-row computation. Same overhead profile,
   but the work moves into a CUDA kernel rather than a Python hook
   per attention call — and the canary can read directly from the
   paged KV cache rather than the just-computed K projection.
2. **vLLM block-manager fork for actual per-layer KV dtype.** The
   tier-application path simulates EchoKV-3C accuracy but doesn't
   give us memory or throughput improvements vs KIVI-4 static. To
   measure those we need vLLM's block manager to maintain three pools
   (INT2/INT4/INT8) and route new allocations through the
   controller's per-layer dtype. Multi-session project (clone vLLM,
   editable install, modify `vllm/v1/core/block_pool.py` and the
   FlashInfer backend's KV cache read/write paths).

The kernel is the smaller engineering effort and unblocks paper claims
about overhead structure ("not implementation-dependent"). The fork is
the larger effort and unblocks paper claims about
memory/throughput Pareto.
