## Tasks

### TASK 1 — ARCHITECTURE.md layer-scoping demotion

The v8.1 finding "layers 21–27 carry the canary signal on RULER-32K"
had crept into ARCHITECTURE.md § 5 as kernel-design guidance ("the
Triton canary kernel may scope to the seven mid-late layers, reducing
the canary's participation in the p_c=1/64 budget by another factor of
~4.5"). This is a category error against the closed-loop premise of
EchoKV: per-layer `b_ℓ` is meant to be discovered dynamically by the
PID controller from the runtime EMA δ̂_ℓ vector. Hardcoding a layer
subset on the kernel breaks both:

1. The closed-loop framing of the paper. If we prebake which layers
   matter, the controller is reduced to a 7-layer dial. The
   contribution claim "EchoKV measures runtime error and responds to
   it" weakens.
2. Generalisation to other models. The v8.1 result is for one model
   (Llama-3.1-8B-Instruct) and one workload (RULER-32K). On
   Nemotron-Nano-V2-12B the high-signal layers may sit at different
   indices because the attention profile differs.

**Edits:**

- `ARCHITECTURE.md` § 5 — removed the "kernel may scope to layers
  21–27" claim. Replaced with: "The canary kernel runs on all 32
  layers at rate p_c=1/64. Per-layer b_ℓ is discovered dynamically by
  the PID controller from the EMA δ̂_ℓ vector; the kernel does not
  hard-code a layer subset."
- `ARCHITECTURE.md` § 9.5 (new) — "Motivation study finding:
  per-layer signal structure". The v8.1 per-layer table is preserved
  here as Figure-1 panel-C evidence. Includes an explicit list of
  reasons the kernel does not pre-scope (model-specificity,
  conversation-specificity, the EMA δ̂_ℓ vector already provides the
  dynamic equivalent).
- `REPORT.md` — same demotion in v8.1 results section + Decision Log.
  Layer subset is explicitly tagged "Figure 1 panel C only", not
  kernel scoping.
- `CHANGELOG.md` — prior session_20260426_2 entry edited to remove the
  scoping claim and reference § 9.5 for the Figure-1 framing.

### TASK 2 — Real canary kernel

Replaced the `canary_paged_attention` stub in
`kernels/canary_attention.py` with a working two-stream
implementation. Operates on dense `(B, H, L, D)` Q/K/V tensors today;
the legacy `k_cache`/`v_cache`/`block_tables`/KIVI scales+zero-points
keyword-arg shape is preserved for the eventual FlashInfer integration
(those extra arguments are accepted but ignored on this code path).

**Behaviour:**

- `is_canary=False`: returns `_kivi4_attention_dense(q, k, v, ...)` —
  the same internal helper used by the test's KIVI-4 reference. INV-4
  holds by construction; both paths run the same code.
- `is_canary=True`: two CUDA streams (serial fallback on CPU):
  * Stream 0 (default): production INT4 path. Quantises K and V via
    `simulate_quantization`, runs FP16 softmax over (Q · K_int4), then
    (w · V_int4) → output and INT4 attention weights ȧ.
  * Stream 1 (canary stream): FP16 reference path. Computes
    ā = softmax(Q · K_fp16 / √d) on the original FP16 K. Runs in
    parallel with Stream 0 because the two paths share no scratch
    tensors; `Stream.wait_stream` synchronises before reduction.
  * δ(ℓ) = mean KL(ȧ ‖ ā), reduced via the new `_kl_rowwise_kernel`
    Triton kernel (one program per row, last dim reduces inside one
    block via `tl.sum`). PyTorch fallback off-CUDA or when the last
    dim exceeds 32K (the BLOCK cap).
  * δ accumulated to `canary_scratchpad` and/or `estimator` (both
    sinks supported simultaneously).

**Validation:**

- INV-4 on CPU: `out - ref` max diff = `0.00e+00` (byte-exact).
- INV-4 on CUDA: `out - ref` max diff = `0.00e+00` (byte-exact).
- Triton-vs-PyTorch KL parity: max diff `2.4e-7` over softmax
  distributions of shape `(2, 4, 8, 64)`. Well within float32.
- δ_paged matches δ_dense within `1e-5` on identical inputs.
- Monotone bit-width ordering holds: δ_INT2 ≥ δ_INT4 ≥ δ_INT8.
- INT8 KL near zero (under `1e-3`) on group-32 quantisation.

### TASK 3 — Estimator wiring

`CanaryEstimator` (`core/canary_estimator.py`) already had EMA + ring
buffer + thread safety from session 3. Wiring is a kwarg pass-through:

- `canary_paged_attention(..., estimator=est)` calls
  `est.observe(layer_id, step, kl, is_canary=True)` on every canary
  fire. Both `canary_scratchpad` and `estimator` can be passed
  simultaneously; they are independent sinks.
- Two new tests cover the integration:
  * `test_canary_kernel_observes_estimator` — kernel fires → EMA
    updates → `ema(layer)` reflects the kernel's recorded KL.
  * `test_canary_kernel_writes_to_both_sinks` — both consumers see the
    same δ on a single fire.

The PID controller will read `estimator.ema(layer)` /
`estimator.snapshot()`; that wiring is session 7 work.

## Bugs found / decisions taken

1. **Original stub raised on `q=None` inputs.** The xfail test in
   `test_invariants.py` called `canary_paged_attention(q=None, ...,
   is_canary=False)`. After implementing the kernel, calling with
   `None` would fault on `q.is_cuda`. Decision: replace the
   placeholder test with a real bit-exactness check using actual
   tensors on both CPU and CUDA. The xfail marker is removed entirely;
   the test now exercises the contract.
2. **Stale `test_paged_stub_raises_not_implemented` in
   `test_kernel_dense_reference.py`.** The stub no longer raises
   `NotImplementedError`; that test had to go. Replaced with a smoke
   check `test_paged_kernel_is_callable` to keep an import-time guard
   in the dense-reference file.
3. **Triton BLOCK_SIZE for `_kl_rowwise_kernel`.** Decided to pick the
   smallest power-of-two ≥ `n_cols` at launch time, capped at 32768.
   Beyond the cap (which `n_cols ≥ 32K` would hit on a 32K-context
   prefill) we fall back to the PyTorch row-wise KL — correct, just
   not Triton-fast. For decode at typical KV-cache sizes (≤32K) the
   Triton path always fires.
4. **Two-stream sync semantics.** The canary stream begins by
   `wait_stream`ing on the default stream so it sees a consistent view
   of inputs (avoids races on freshly-written tensors). The default
   stream then `wait_stream`s on the canary stream before the KL
   reduction. No race possible because each stream writes to its own
   output tensor.
5. **`block_tables`/scales/zero-points kwargs.** Kept them in the
   signature even though they're unused on the current dense code
   path. When FlashInfer is pinned, the kernel's INT4 path will
   consume them directly. Documented in the docstring.

## What session 7 should start with

The canary kernel is producing real δ on real GPU inputs and writing
into the estimator's EMA. Session 7 hands the EMA off to the
controller and broadcasts the controller's per-layer `b_ℓ` decisions.

1. **PID precision controller** (`core/precision_controller.py` —
   stub today). Implement the discrete update law from
   ARCHITECTURE.md § 4.2:
   - Read `estimator.snapshot()` per controller tick (every N_c=100
     decode steps).
   - Compute `τ_eff = τ · g(kv_utilization, precision_budget)` with
     `g` monotone non-decreasing in utilisation, monotone non-
     increasing in budget.
   - Hysteresis: 20% band per level boundary (INT2↔INT4↔INT8).
   - Emit per-layer target precision `b_ℓ ∈ {2, 4, 8}` to the
     allocator (which already has the precision-aware free-list
     plumbing from session 1).
   - INV-2 audit: the controller must not have any
     refresh/repair/rewrite/migrate symbol on its public surface
     (test guard already in place).

2. **SLO budget plumbing** (`core/slo_budget.py` — stub today).
   `broadcast_precision(levels, tp_world_size)` is the call point that
   currently makes INV-3 xfail. To flip INV-3:
   - Wire it through a fake TP harness in tests
     (`tests/test_inv3_*` style) that asserts all simulated ranks
     observe the new precision vector before any rank admits the next
     decode step.
   - For real TP this lands behind vLLM's scheduler; the mock harness
     is enough to flip the xfail.

3. **End-to-end loop test.** Once the controller and SLO budget are
   wired, write an integration test that runs:
   `kernel → estimator → controller → allocator → kernel` on synthetic
   QKV traces over ~200 decode steps and asserts the controller
   converges (δ̂ stays inside ±20% of τ on a stable workload).

4. **Per-layer scoping is the controller's job, not the kernel's.**
   When testing the controller, verify it converges on higher
   precision for layers ~21–27 on RULER-style traces (the v8.1
   prediction). If it does, that's a falsifiable success of the
   closed-loop story; if it doesn't, the controller's update law or
   the τ_eff function needs revisiting before the kernel is rerun.

5. **FlashInfer pinning.** The current kernel works on dense tensors;
   FlashInfer integration replaces the dense matmuls with paged-decode
   primitives. CHANGELOG's "FlashInfer TBD (pin at first use)" line is
   ready to be filled in once we wire it. The two-stream structure and
   the Triton KL kernel stay; the dense `_kivi4_attention_*` helpers
   become reference paths only.
